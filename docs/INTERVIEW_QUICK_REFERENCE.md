# Enterprise LLM Wiki 面试速记卡

> 2026-09-09 · 完整技术依据与边界见 [架构与面试手册](INTERVIEW_HANDBOOK.md)。以下话术需要按你本人实际负责范围调整，不把 AI 辅助完成或尚未验证的工作夸大为个人独立成果。

## 30 秒介绍

我做的是一个企业级 LLM Wiki。成员提交资料后，由 AI 整理成相互关联的知识页面，而不只是提供一次文档问答。项目重点是多人协作、已有知识更新的审核、来源追溯和持续维护。架构采用 React、Java 模块化单体、独立 Python 提取服务和 PostgreSQL，另有持久化会话、定时任务、MCP 和 Obsidian 导出。

## 两分钟介绍

这个项目解决的是企业资料很多，但长期可复用知识难以维护的问题。我在 LLM Wiki 思路上增加了企业协作和变更治理：多人提供资料，AI 做整理，已有知识的变化先生成提案，再审核发布。

架构上，Java 负责认证、组织、权限、事务和任务状态，Python 隔离文档解析、OCR 和转写依赖，React 提供统一界面。PostgreSQL 保存页面、来源版本、修订、证据与审核，原始文件在本地对象目录，Redis 只保存可重建缓存。

核心流程是来源和任务先登记，后台通过数据库锁与租约领取任务，再在事务外调用 Python 和模型，处理结果形成多页面变更集。审核时检查基线修订，避免旧提案覆盖新内容。已有页面更新必须审核，全新内容则按权限决定发布方式。

问答检索的是已发布 Wiki：关键词检索与本地 BGE 语义向量召回通过 RRF 融合，再做一跳关系扩展。向量保存在 PostgreSQL real[]，不依赖独立向量数据库；发布后自动生成，审核更新后旧索引立即失效。回答带引用，消息任务化保存，因此浏览器关闭后后台仍能继续。详见 [语义检索说明](SEMANTIC_RETRIEVAL.md)。

我的重点是把不稳定的 AI 输出接进可追踪、可审核的业务流程。当前仍有生产化边界，例如租约提交 fencing、Redis 缓存一致性和检索评测需要补强；我不会把它包装成已经压测过的高并发 SaaS。

## 六条记忆主线

1. **定位**：长期知识编译，不只是一次问答。
2. **事实**：来源版本、当前页面、历史修订、证据。
3. **治理**：提案与发布分离，旧基线不能覆盖新页面。
4. **异步**：领取短事务、外部处理、提交短事务；租约不是恰好一次。
5. **查询**：先查已发布 Wiki，再组织回答；有引用不等于零幻觉。
6. **边界**：Java 治理、Python 提取、数据库事实、缓存派生、知识可导出。

## 最值得主动讲的三项亮点

- 把“让 AI 自己改文件”的维护约定落成可审计的企业发布流程。
- 定时采集、摄取编译和人工审核复用同一主链路，减少业务旁路。
- 会话计算持久化为后台任务，前端离开不等于回答过程被取消。

这是工程设计价值，不是新算法或行业首创。

## 最容易说错的十句话

| 不要说 | 准确说法 |
| --- | --- |
| 我实现了完整 GraphRAG | 目前是 WikiLink 一跳关系增强检索 |
| 每个回答都绝对可信 | 候选引用真实，但仍缺逐结论验证 |
| AI 一定只能由人批准 | 有审核权限的身份可调用审核 API，包括 MCP；需额外落实职责分离 |
| 有租约就绝不重复执行 | 仍需 fencing、幂等和失效处理 |
| 每次领四个就是并发四个 | 是每轮领取量，不是全局在途上限 |
| Redis 挂了完全不影响一致性 | 可降级，但跨资源失效仍有旧缓存窗口 |
| 有 Outbox 就是消息恰好一次 | 当前发布到日志，业务与事件记录同事务 |
| 只读事务就是一致快照 | 还取决于隔离级别与读取方式 |
| 定时任务成功就是知识已发布 | 生成资料、编译、审核发布是不同阶段 |
| 高并发提升了某个百分比 | 未测就不给数字，说明测量方案 |

## 三分钟演示顺序

1. 工作台：说明已发布知识、来源、待审与活动。
2. 知识库：打开模型/专题，展示关联和来源；手工页没有自动证据时如实说明。
3. 知识图谱：点击厂商，查看旗下模型及相关专题。
4. 问 Wiki：展示会话及引用，明确是实时回答还是历史记录。
5. 审核中心：展示差异，并用 A/B 提案基线冲突说明并发设计。
6. 定时任务：展示频率、启停、执行记录，解释失败与待审核不是成功发布。

演示前检查模型余额、连通性和样例数据；不能为演示伪造运行成功。本次未执行这些检查。
