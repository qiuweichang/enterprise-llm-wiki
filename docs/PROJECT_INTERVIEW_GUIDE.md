# Enterprise LLM Wiki 项目全景与面试讲解

> 2026-09-09 更新提示：已新增基于当前代码复核的 [架构与面试手册](INTERVIEW_HANDBOOK.md) 和 [面试速记卡](INTERVIEW_QUICK_REFERENCE.md)。本文保留原始讲解；缓存强一致、租约提交保证、引用真实性、导出快照与人工审核边界请以新版说明为准，勿把原设计意图直接视为已验证保证。

> 目标：不背具体代码，也能讲清项目定位、架构选择、核心链路、数据一致性、安全机制、故障恢复，以及当前边界。

## 一句话定义

Enterprise LLM Wiki 是一个面向企业的、多租户、可审核、可追溯的知识编译系统。它把成员提交的文本、网页、文件、音视频持续转换成长期维护的 Wiki 页面、页面关系和证据链，再提供带引用的问答、持续优化、MCP 接入和 Obsidian 导出。

它和普通“上传文档后临时问答”的 RAG 最大区别是：

- 普通 RAG 的中心是“切片、检索、临时生成答案”。
- 本项目的中心是“来源、编译、页面、修订、证据、审核、发布”。
- 查询读取的是已经发布的 Wiki，而不是每次重新把全部原始资料交给模型。
- AI 负责生成候选知识，人负责控制已发布知识的变更。

## 30 秒面试话术

这个项目采用 React、Spring Boot、Python Worker 和 PostgreSQL 的组合。Spring Boot 是模块化单体，承载认证、权限、来源、Wiki、审核、查询、自动化和导出等强事务业务；Python Worker 隔离网页解析、PDF/DOCX、OCR 和音视频转写等依赖重、稳定性差异大的工作；PostgreSQL 是唯一事实源，同时保存不可变来源版本、不可变页面修订、证据、审核、任务和审计。后台任务不用独立 MQ，而是用数据库任务表、`SKIP LOCKED`、租约和指数退避实现可靠调度。长耗时的 Python 和大模型调用都在事务外执行。已有知识的更新不会被 AI 直接覆盖，而是进入审核，批准时再通过基线修订、行锁和乐观版本检查原子发布。

## 一、系统边界

### 1. React 管理台

职责是企业成员的操作界面，包括登录、工作空间切换、仪表盘、知识页面、来源、问 Wiki、审核、持续优化、AI 定时任务、知识图谱、成员和模型设置。

前端使用 React Router 管理页面，TanStack Query 管理服务端状态。短期访问令牌只保存在内存中；刷新令牌放在 HttpOnly Cookie。遇到 401 时，API 层会把并发刷新合并为一次刷新请求，刷新成功后重试原请求。

前端权限隐藏只改善体验，不是安全边界。真正的权限判断始终在后端执行。

### 2. Java 模块化单体

Spring Boot 服务是业务核心。选择模块化单体而不是一开始拆微服务，是因为页面、修订、证据、变更集、审核、审计和 Outbox 需要强事务一致性。它们在一个数据库、一个事务边界中更容易保证正确性，也减少早期分布式事务和服务治理成本。

内部按领域分包，主要包括：

- 认证与组织：登录、刷新、会话、API Key、组织、工作空间、成员、角色和权限。
- 来源：文本、URL、文件、音频、视频登记，来源版本和摄取任务。
- Wiki：页面当前投影、不可变修订、WikiLink 关系索引和图谱。
- 审核：变更集、变更动作、批准、驳回、并发冲突处理。
- 查询：混合检索、图邻居扩展、引用回答、缓存和持久化会话。
- 自动化：URL 自动刷新、持续优化、AI 定时资料任务。
- 导出：一致快照和 Obsidian Vault ZIP。
- 审计与 Outbox：业务审计和领域事件。

### 3. Python FastAPI Worker

Python 服务只做内容提取，不掌握最终业务状态：

- 网页：抓取 HTML，清理脚本、导航等噪声，主内容转 Markdown。
- 文档：TXT、Markdown、HTML、DOCX、PDF 等格式提取。
- OCR：普通 PDF 提取不到文字时转图片 OCR，也支持图片 OCR。
- 音视频：通过可选的 faster-whisper 生成带时间戳的转写文本。

把这部分独立出来有三个原因：Python 生态更适合文档和模型工具；OCR、转写依赖重；解析失败或模型占用显存时，不应该污染 Java 主业务进程。

### 4. PostgreSQL

PostgreSQL 是唯一事实源，不只是普通业务库，还承担四种职责：

- 领域事实：组织、空间、来源、页面、修订、证据、审核、审计。
- 检索：`tsvector` 全文索引、`pg_trgm` 标题相似度和正文包含匹配。
- 可靠任务：摄取、会话问答、持续优化和 AI 定时任务的状态与租约。
- 租户隔离：`FORCE ROW LEVEL SECURITY` 和事务级组织、空间上下文。

### 5. Redis

Redis 只保存可丢失、可重建的查询缓存。缓存键包含组织、空间、知识版本戳和问题内容哈希。页面发布后只递增工作空间 epoch，旧缓存自然失效，不需要扫描和删除一批通配键。

Redis 故障时系统回源 PostgreSQL，因此影响性能，不影响事实正确性。

### 6. 外部大模型

系统通过统一的 OpenAI Compatible Chat Completions 客户端调用模型。模型配置按工作空间保存，数据库配置优先于环境配置，API Key 使用 AES-GCM 加密。

模型用于三类任务：

- 把来源编译成中心主题页和实体页。
- 根据检索到的 Wiki 页面生成带引用回答。
- 检查已发布页面的矛盾、过时点并生成维护提案。

模型不是事实源，也不能绕过审核直接修改已有页面。

## 二、来源摄取到知识发布的完整流程

这条链路是项目最核心的主流程。

### 第 1 步：登记来源

用户提交文本、URL 或上传文件。Java 服务校验类型、标题、URL 或文件信息，并在同一个短事务中写入：

- `sources`：来源的当前元数据和处理状态。
- `source_versions`：不可变来源版本；直接文本和上传文件可立即产生首个版本。
- `ingestion_jobs`：待处理摄取任务。
- `audit_logs`：谁创建了什么来源。
- `outbox_events`：来源已创建的领域事件。

这样不会出现“来源创建成功，但排队失败，所以永远不处理”的半状态。

上传文件先进入本地对象存储，文件名和对象路径会被清理、规范化并限制在配置根目录内。部署时可以把同一抽象替换为 S3 或 MinIO。

### 第 2 步：领取任务

摄取协调器定时扫描任务表，每次最多领取有限数量任务。领取通过一条原子 SQL 完成：

- 选择到期的 `PENDING`，或租约已经过期的 `PROCESSING` 任务。
- 使用 `FOR UPDATE SKIP LOCKED`，不同实例不会领取同一行，也不会互相等待。
- 更新为 `PROCESSING`，增加尝试次数并写入租约持有者和过期时间。
- 事务随即提交，数据库行锁立即释放。

这是一种数据库可靠队列。任务表保存事实，`SKIP LOCKED` 负责多实例分片，租约负责实例宕机后的接管。

### 第 3 步：事务外内容提取

任务交给 Java 虚拟线程执行。Java 根据来源类型分流：

- TEXT：直接复用已保存 Markdown。
- URL：调用 Python `/extract/web`。
- FILE：调用 Python `/extract/file`。
- AUDIO、VIDEO：调用 Python `/transcribe`。

网络调用不在数据库事务中，因此 Python 处理慢、OCR 慢或模型请求慢时，不会长时间占用数据库连接和行锁。

### 第 4 步：内容安全处理

网页抓取会校验 HTTP/HTTPS、拒绝 URL 内嵌凭据、解析全部 DNS 结果，并默认拒绝私网、环回、链路本地、保留和特殊地址。每次重定向都会重新校验，防止通过跳转绕过 SSRF 防护，并限制最大下载体积和跳转次数。

本地文件读取会把目标路径解析为绝对路径，并确认它仍在共享存储根目录内，防止路径穿越读取系统文件。

### 第 5 步：知识编译

清洗后的 Markdown 交给 Knowledge Compiler。它优先调用空间配置的大模型，要求模型返回结构化的多页面结果：一个中心主题页，加若干可以独立复用的实体或综合页面。页面之间通过 `[[WikiLink]]` 建立语义连接。

如果模型未配置、调用失败、额度不足或返回结构不合法，系统不会直接丢失摄取任务，而是进入确定性降级：根据 Markdown 二级、三级标题拆分知识边界，过滤“简介、背景、总结”等过泛标题，生成中心页和有限数量的实体页。

这个降级保证“没有模型时仍能把资料变成可审核 Wiki”，只是知识质量和综合能力低于模型编译。

### 第 6 步：形成变更集

编译结果回到一个新的短事务中。系统会：

- 根据内容哈希判断是否需要创建新的来源版本。
- 把来源更新为 `READY`。
- 按页面 slug 查找是否已有已发布页面。
- 为整批候选页面创建一个 `change_set`。
- 为每个候选页创建 `change_set_action`，动作是新增或更新。
- 更新摄取任务为成功，并写审计和 Outbox。

内容哈希用于去重和内容身份判断，但业务版本仍通过版本号和不可变记录表达。

### 第 7 步：决定直接发布还是进入审核

规则不是“AI 置信度高就直接发布”，而是权限和知识状态共同决定：

- 只包含全新页面，并且提交者有 `PAGE_CREATE_PUBLISH` 权限时，可以直接发布。
- 任何已有页面更新都必须进入 `PENDING` 审核。
- 新页面权限不足时也必须审核。

直接发布时，系统在同一事务中创建页面、第一版不可变修订和来源证据，再重建 WikiLink 关系，并推进 Redis workspace epoch。

### 第 8 步：人工审核与原子发布

审核批准时先锁定变更集，保证同一提案只被决策一次。对于多页更新，系统按页面 UUID 固定排序后逐页加锁，降低死锁风险。

每个更新动作都校验提案的 `base_revision_id` 是否仍等于页面当前修订：

- 相同：说明审核期间页面未变化，可以继续发布。
- 不同：说明页面已经被其他变更更新，整个提案标记为 `SUPERSEDED`，不能覆盖新知识。

真正更新页面时还带有 `version` 和当前修订条件。也就是说，系统同时用了：

- 悲观行锁：阻止审核发布阶段并发修改。
- 基线修订检查：判断提案是否基于过期内容。
- 乐观版本检查：兜底检测异常并发写。

批准后一次事务完成新修订、页面当前投影、证据、关系、审核记录、审计和 Outbox。驳回只改变提案状态和审计，不修改已发布页面。

## 三、问 Wiki 的完整流程

### 第 1 步：会话排队

前端创建会话或追加问题时，系统在同一事务中保存：

- 一条已经完成的用户消息。
- 一条 `PENDING` 的助手消息。

数据库部分唯一索引保证同一会话最多只有一条正在排队或运行的助手消息，避免重复回答和消息顺序混乱。

后台协调器领取助手消息后，即使浏览器关闭，回答仍会继续执行。租约过期后其他实例可以接管。

### 第 2 步：规范化和缓存

问题先做 Unicode NFKC 规范化并压缩空白。缓存键包含：

- 组织 ID 和工作空间 ID。
- 当前 workspace epoch。
- 检索文本、最近会话上下文和是否使用模型的内容哈希。

命中缓存后仍会记录一次查询运行，便于统计和审计。

### 第 3 步：混合检索

当前实现没有向量数据库，也没有 embedding。它使用 PostgreSQL 的组合检索：

- `tsvector` 和 `websearch_to_tsquery('simple', ...)` 做全文检索。
- `pg_trgm` 做标题模糊匹配。
- `ILIKE` 正文包含匹配弥补中文简单分词不足。
- 按相关度和更新时间排序，最多取 8 个主页面。
- 再通过 `wiki_relations` 扩展一跳邻居，最多补充 4 个关联页面。

如果主检索完全没有命中，会退化到最近更新的已发布页面，避免回答链路得到空上下文。

### 第 4 步：回答生成

检索结果先生成修订级引用，包括页面 ID、slug、标题、修订号和摘要。

允许使用模型时，模型只能基于给定 Wiki 页面回答，并被要求使用 `[1]` 形式引用；最近会话只帮助理解追问，不能作为事实来源。

三种主要回答模式：

- `AI`：模型基于 Wiki 上下文生成回答。
- `EXTRACTIVE`：模型不可用或用户关闭模型时，直接组合高相关页面的可核验摘要。
- `NO_KNOWLEDGE`：没有可用知识时明确告诉用户信息不足。

模型额度异常有单独状态和友好提示，不会伪装成正常 AI 回答。

### 第 5 步：持久化结果

回答、引用、是否命中缓存、耗时、回答模式、模型提供商和模型名会写入消息及查询运行记录。这样面试时可以强调：系统不只保存聊天文本，还保存回答是怎么产生的。

## 四、持续优化流程

持续优化不是让模型自由改 Wiki，而是一个“巡检并提案”的受控流程。

1. 管理员开启空间级持续优化，最短周期 30 分钟。
2. 调度器每分钟扫描到期空间，并通过活动任务唯一索引保证每个空间最多一轮活动任务。
3. Worker 通过租约领取运行。
4. 读取一批已发布页面快照，优先选择从未扫描或最久未扫描的页面，轮转覆盖整个 Wiki。
5. 在事务外让模型检查矛盾、过时内容和结构问题。
6. 回库时重新锁定页面并校验基线修订。
7. 对仍有效的结果创建 `MAINTENANCE` 变更集，状态为待审核。
8. 人工批准后才复用统一审核发布事务生成新修订。

运行记录长期保留触发方式、模型、扫描页数、矛盾数、提案数、变更集和错误。如果模型未配置，运行记为跳过；如果密钥失效或额度不足，持续优化会暂停，避免每分钟重复失败。

## 五、AI 定时资料任务

AI 定时任务支持每天、每周和固定间隔。它的关键设计是“模型输出不能直接成为 Wiki 事实”。

流程如下：

1. 调度器扫描到期任务并创建运行记录。
2. 运行通过数据库租约领取，在事务外调用模型。
3. 厂商资讯任务会先通过 Python 抓取经过代码审查的官方页面，再把证据交给模型整理。
4. 模型输出先转成一个不可变 TEXT 来源和来源版本。
5. 同事务创建普通 `ingestion_job`。
6. 后续完全复用来源摄取、知识编译、证据和审核链路。

这样避免了另一套“AI 任务直接写页面”的旁路。模型调用成功只代表结果进入摄取队列；后续编译成功或死信还会反向更新任务运行摘要，防止表面成功、实际未入库。

## 六、认证、权限与租户隔离

### 1. 登录与令牌

- 密码使用 BCrypt 验证。
- 访问令牌是短期 JWT。
- 刷新令牌仅放在 HttpOnly Cookie，数据库只保存 SHA-256 摘要。
- 每次刷新都轮换刷新令牌。
- JWT 里包含候选身份，但后端仍重新读取数据库会话、用户状态、组织成员和空间成员状态。
- 用户 `token_version` 可以让旧令牌整体失效。

### 2. MCP API Key

MCP 可以使用 JWT，也可以使用 `lwk_` API Key。API Key 绑定用户、组织和空间，可撤销、可过期；数据库保存哈希，原始值只在创建时返回一次。认证后权限仍实时读取 RBAC。

### 3. RBAC

控制器通过权限声明定义所需能力，授权拦截器从当前身份判断权限。角色只是权限集合，既有系统角色，也支持组织自定义角色。

### 4. PostgreSQL RLS

关键内容表都带 `organization_id` 和 `workspace_id`，并启用 `FORCE ROW LEVEL SECURITY`。进入租户事务后，服务会：

1. `SET LOCAL ROLE llm_wiki_app`，即使开发连接使用超级用户，也在当前事务立即降权。
2. 设置当前组织和工作空间到事务本地 PostgreSQL 参数。
3. RLS 策略只允许访问与当前参数一致的行。

`SET LOCAL` 的作用域只到当前事务，连接回到连接池后不会把上一位用户的租户上下文泄漏给下一位用户。

这是“应用显式条件 + RBAC + 数据库 RLS”的纵深防御。即使某条业务 SQL 忘记写租户条件，RLS 仍提供最后防线。

## 七、数据模型应该怎么讲

面试时不必背所有表，可以按六组概念记忆：

| 数据组 | 关键实体 | 作用 |
|---|---|---|
| 身份与组织 | users、organizations、workspaces、members、roles、permissions、sessions、api_keys | 身份、组织层级、RBAC 和会话 |
| 来源 | sources、source_versions | 来源当前状态和不可变版本 |
| 知识 | wiki_pages、wiki_page_revisions、evidence、wiki_relations | 当前页面投影、历史修订、证据和关系 |
| 变更治理 | change_sets、change_set_actions、reviews | 把候选知识和正式发布解耦 |
| 异步运行 | ingestion_jobs、query_messages、wiki_evolution_runs、ai_scheduled_task_runs | 排队、租约、状态、错误和运行历史 |
| 可观测与集成 | query_runs、audit_logs、outbox_events | 查询记录、审计和领域事件 |

`wiki_pages` 是为了快速读取的当前投影，`wiki_page_revisions` 才是不可变历史。二者并存，兼顾查询效率和追溯能力。

`wiki_relations` 不是独立事实源。正文中的 WikiLink 才是关系事实，关系表只是为了图谱和邻居检索而建立的派生索引，可以从 Markdown 重建。

## 八、一致性、并发和故障恢复

### 1. 为什么网络调用一定在事务外

如果把 OCR、网页抓取或大模型请求放进事务，会长时间占用数据库连接和锁；外部服务的超时还会扩大数据库拥塞。项目把流程拆为：

`短事务领取 → 事务外执行 → 短事务提交`

代价是需要任务状态、租约和幂等控制，但换来了更好的吞吐、故障隔离和多实例接管。

### 2. 租约为什么比单纯状态更可靠

只有 `PROCESSING` 状态时，Worker 宕机后任务会永久卡住。租约增加 `lease_owner` 和 `lease_until`：处理者必须在自己仍持有租约时提交；租约过期后其他实例可以重新领取。

### 3. 重试与死信

摄取失败后，根据尝试次数回到 `PENDING` 或进入 `DEAD`。下一次时间使用指数退避，并设置最大延迟，避免外部服务故障时形成请求风暴。达到最大次数后来源标记失败，管理员能看到明确原因。

### 4. Outbox

业务状态和 Outbox 事件在同一事务提交，避免“数据库成功但消息没发”或“消息发了但数据库回滚”。当前发布器只把事件输出为结构化 info 日志，并标记为已发布；未来接 Kafka、RabbitMQ 等消息中间件时可以保留同一事件表和领取语义。

要诚实说明：当前 Outbox 发布器还不是完整生产级消息发布器，没有看到发送外部 Broker、失败重试和死信策略的完整实现。

## 九、当前项目的真实边界

这些点很适合在面试中主动说明，体现你理解“完成了什么”和“还没完成什么”。

- 当前是模块化单体，不是微服务系统。
- 当前检索是 PostgreSQL 全文、三元组、包含匹配和一跳图扩展，没有 pgvector，也没有独立向量数据库。
- Redis 只是派生缓存，不是事实源。
- 任务队列在 PostgreSQL 中，没有 Kafka、RabbitMQ 或 Redis Stream。
- 对象存储当前是本地共享目录，尚未切换 S3/MinIO。
- Python Worker 依赖 Java 与它共享对象存储；正式部署需要内部网络隔离、服务鉴权或网关保护。
- Outbox 当前发布到日志，还没有接真正的消息中间件。
- 模型接口走 OpenAI Compatible Chat Completions，不是绑定某一家模型厂商。
- 中文检索用 `simple` 字典时能力有限，正文包含和标题三元组只是补偿方案。
- 导出是数据库到 Markdown/Obsidian 的单向投影，不支持双向同步。
- 项目 README 明确把容器化、CI/CD、完整监控告警和可选向量索引列为后续方向。

## 十、为什么这些设计成立

### 为什么选模块化单体

知识发布横跨页面、修订、证据、审核、审计和事件，强一致性要求高。单体可以用本地事务直接保证原子性，团队早期也更容易开发和排错。Python 只在依赖边界处拆服务，是按变化频率和运行时差异拆，而不是为了微服务而拆。

### 为什么来源版本和页面修订都不可变

来源版本回答“这条知识当时基于哪份资料”，页面修订回答“用户当时看到的是哪一版结论”。两条不可变链通过 evidence 连接，才能真正做到审计、回溯和引用核验。

### 为什么现有页面必须审核

新知识发布错误主要影响新增内容，已有页面更新却可能破坏已经被其他人依赖的结论。项目把“生成候选”和“发布事实”分开，AI 只提案，人控制覆盖风险。

### 为什么关系表是派生索引

如果正文和关系表都能独立修改，会形成双主写和不一致。项目以 WikiLink 正文为事实源，发布后统一重建关系表；图谱与邻居检索可以加速，但关系可以恢复。

### 为什么缓存用 epoch

发布一批知识后，如果逐个寻找并删除所有相关查询键，成本高且容易漏。把 epoch 放进缓存键，发布只需要一次原子自增；旧键不再被命中，等待 TTL 自然淘汰。

## 十一、常见面试追问与回答

### 1. 这是 RAG 吗？

它有 RAG 的检索和基于上下文生成，但核心不只是 RAG。系统先把原始资料编译成长期维护、可审核的 Wiki，再对已发布 Wiki 做检索增强回答。可以称为“知识编译 + 治理 + 检索问答”。

### 2. 为什么不用向量数据库？

当前目标优先保证可追溯主链路和较低基础设施复杂度，所以先用 PostgreSQL 全文、标题三元组、正文包含和图邻居满足基础检索。向量索引可以作为派生层增加语义召回，但不能替代已编译 Wiki、修订和证据链。

### 3. 多实例会重复处理任务吗？

领取阶段用 `FOR UPDATE SKIP LOCKED` 原子选择和更新任务，并写租约。正常情况下只有一个实例持有任务；实例崩溃后租约过期可接管。最终提交还检查租约持有者。严格来说外部调用可能因为租约过期被重复执行，所以结果写入仍依赖唯一约束、状态条件和幂等设计控制副作用。

### 4. 为什么不用消息队列？

项目当前任务量和一致性需求适合数据库队列：业务事实和任务可以同事务落库，部署简单，也支持 `SKIP LOCKED` 多实例消费。规模更大、需要跨系统广播和更高吞吐时，可以把 Outbox 接到专用消息中间件。

### 5. AI 生成错误怎么办？

已有知识永远不能被 AI 直接覆盖；模型输出先进入变更集，人工审核后发布。回答阶段模型只能看已发布 Wiki，信息不足必须说明；模型不可用时可以退化为抽取式答案。所有引用指向具体页面修订。

### 6. 审核期间页面被别人更新怎么办？

提案保存基线修订。批准时锁定页面并比较当前修订；如果不一致，提案标记为 `SUPERSEDED`，要求基于最新版重提。更新语句还有 `version` 和当前修订条件作为乐观并发兜底。

### 7. 怎么保证租户数据不串？

请求层校验身份和 RBAC，SQL 通常显式带组织和空间键；进入事务还设置租户上下文，由 PostgreSQL `FORCE RLS` 做最后隔离。开发即使用超级用户连接，也会在事务内切换到非超级用户角色，让 RLS 真正生效。

### 8. Redis 挂了怎么办？

缓存服务捕获 Redis 读写异常并记录错误，查询回源 PostgreSQL。Redis 中没有不可恢复的业务事实，因此正确性不受影响，只是性能下降。

### 9. 模型挂了怎么办？

来源编译会使用确定性 Markdown 章节拆分；问答会使用抽取式答案；持续优化会记录跳过或失败并在关键配置问题时暂停；任务状态和错误仍会持久化，不会把失败伪装成成功。

### 10. 为什么同时保存页面当前内容和修订历史？

当前内容是读模型，页面列表、检索和详情无需每次联表找最新版；修订表是不可变历史，用于审计、引用和并发基线。发布事务同时写两者，保证投影和历史一致。

### 11. 怎么避免死锁？

多页审核在加锁前按页面 UUID 固定排序，让不同事务以相同顺序获得锁。事务范围也尽量短，外部调用完全移出事务。

### 12. 网页抓取如何防 SSRF？

只允许 HTTP/HTTPS，禁止内嵌凭据，解析并检查全部 DNS 地址，默认拒绝私网、环回和特殊地址；手工处理重定向并对每一跳重新校验；同时限制跳转次数、下载大小和请求超时。

### 13. 为什么 Python Worker 不直接写数据库？

Python 只负责不稳定的内容提取，Java 负责领域状态和事务。这样业务规则只有一个入口，不会出现 Python 和 Java 各自修改来源、修订或审核状态造成的双写和语义漂移。

### 14. 怎么保证引用可信？

回答引用来自实际检索到的已发布页面，并带页面 ID、slug、标题和修订号。页面修订再通过 evidence 关联到来源及来源版本，所以可以从回答追到修订，再追到原始资料版本。

### 15. 如果要继续演进，你会先做什么？

优先级可以是：把本地对象存储替换为 S3/MinIO；为 Python Worker 增加正式的服务间认证和隔离；补充指标、链路追踪、告警和任务运营面板；把 Outbox 接入消息中间件；基于评测数据增加中文分词和可选 pgvector 语义召回；最后再根据团队和流量决定是否拆分服务。

## 十二、面试时推荐的讲解顺序

1. 先说业务痛点：企业知识要长期维护、可审核、可追溯，而不是一次性聊天。
2. 再说架构边界：React、Java 模块化单体、Python Worker、PostgreSQL、Redis、外部 LLM。
3. 重点走一遍来源到发布链路。
4. 再讲问 Wiki 如何检索、引用和降级。
5. 用租约、短事务、`SKIP LOCKED` 讲并发和故障恢复。
6. 用不可变版本、证据、审核、Outbox 讲一致性和治理。
7. 用 JWT/API Key、RBAC、RLS、SSRF 防护讲安全。
8. 最后主动说清当前没有向量库、没有 MQ、本地对象存储等边界和演进方向。

## 十三、两分钟完整陈述模板

我做的是一个企业级 LLM Wiki。它不是简单的上传文档问答，而是把企业成员提交的文本、网页、文件和音视频持续编译成可维护的 Wiki 页面。每一条知识都能追溯到来源版本，已有页面的修改必须经过审核。

架构上，前端是 React，Java 21 和 Spring Boot 负责所有强事务领域逻辑，Python FastAPI 隔离网页解析、文档、OCR 和音视频转写，PostgreSQL 是唯一事实源，Redis 只做可丢失的查询缓存。大模型通过 OpenAI Compatible 接口按工作空间配置。

核心摄取流程是：来源、来源版本和任务同事务落库；后台通过 `SKIP LOCKED` 和租约领取任务；Python 和大模型在事务外执行；结果回库后形成一个多页面变更集。全新页面在具备权限时可以直接发布，但任何已有页面更新都必须人工审核。批准时会同时检查基线修订、行锁和乐观版本，避免旧提案覆盖新内容；新修订、页面投影、证据、关系、审核、审计和 Outbox 在同一事务提交。

问答流程会先做 workspace epoch 缓存，然后用 PostgreSQL 全文索引、标题三元组、正文包含和一跳知识图谱扩展检索已发布页面，最后由模型生成带修订级引用的回答。当前没有向量数据库；模型不可用时会退化为可核验的抽取式回答。

系统还支持持续优化和 AI 定时任务，但 AI 结果不会直接覆盖 Wiki：持续优化只生成审核提案，定时任务结果先变成不可变来源，再复用统一摄取和审核链路。多租户则通过数据库会话校验、RBAC、事务级租户上下文和 PostgreSQL FORCE RLS 多层保障。

如果时间很紧，只记住下面六组关键词：

- 定位：持续知识编译，不是临时文档问答。
- 事实：来源版本、页面修订、证据链，PostgreSQL 唯一事实源。
- 治理：AI 只提案，已有知识必须审核。
