>
> 推荐先读 [面试速记卡](INTERVIEW_QUICK_REFERENCE.md)，技术追问再查本手册。旧版 `PROJECT_INTERVIEW_GUIDE.md` 保留历史内容；涉及一致性、租约、引用可信度的表述，以本手册的边界说明为准。

## 1. 项目定位：先讲业务，不先背技术栈

**一句话：我做的是一个企业知识编译与治理系统，让多人提供资料、AI 持续整理知识，已有知识经过审核后更新，并支持带引用的查询。**

解决三个问题：

1. 材料多但知识分散：网页、文件、文档和成员经验没有形成可复用的主题与实体。
2. Wiki 难维护：新资料出现后，相关页面、链接和旧结论需要持续更新。
3. 企业不能只相信模型输出：需要权限边界、来源、审核、历史和失败记录。

### 与文档问答、个人式 LLM Wiki 的区别

| 对比维度 | 本项目的定位 |
| --- | --- |
| 与典型文档切片问答相比 | 在原始资料与问答之间增加长期维护的 Wiki 页面层，把整理成果持久化，而不只保留一次回答。 |
| 与个人 Agent + Markdown 相比 | 把个人维护约定变成组织、空间、角色、提案、审核和后台任务等应用机制。 |
| 与普通人工 Wiki 相比 | AI 承担初步整理、关联和巡检，成员负责提供资料与判断变更。 |
| 是否完全取代 RAG | 不是。问答仍包含检索增强生成，只是当前主要检索已发布 Wiki。两种方法可以组合。 |

不要说“所有 RAG 都没有积累”“普通 llm-wiki 都不支持审核”。原始 LLM Wiki 思路本身就可以用于团队，产品差异在具体落地，而非独占理念。

## 2. 系统架构与职责

当前是 **Java 模块化单体 + 独立 Python 提取服务**，不是微服务集群，也不是多智能体平台。

| 层次 | 当前组成 | 主要职责 | 不承担什么 |
| --- | --- | --- | --- |
| 操作入口 | React 19、TypeScript、React Router、TanStack Query | 页面、图谱、会话、审核和管理操作 | 前端隐藏按钮不充当安全边界 |
| 集成入口 | `/mcp` JSON-RPC POST | 外部 AI 工具调用查询、来源、页面、审核能力 | 不另建一套绕过审核的数据写入通道 |
| 业务层 | Java 21、Spring Boot、Spring JDBC | 认证授权、租户上下文、领域规则与事务 | 不把文件解析生态全部搬进 Java |
| 异步编排 | Spring 定时扫描、数据库任务表、虚拟线程 | 领取任务、外部调用、保存结果 | 不是已接入 Kafka/RabbitMQ 的消息系统 |
| 内容提取 | Python FastAPI | 网页、DOCX/PDF、图片 OCR、可选音视频转写 | 不直接决定页面是否发布 |
| 模型调用 | 工作空间级 OpenAI Compatible 客户端 | 内容编译、回答、维护分析、资料整理 | 模型不是事实库，也不应获得无限写权限 |
| 业务事实 | PostgreSQL | 页面、来源版本、修订、证据、提案、任务与审计 | 不等于所有二进制文件都在数据库里 |
| 原文件 | 本地对象目录 | 保存上传原文件 | 与数据库不具有天然的跨资源原子事务 |
| 缓存 | Redis | 查询结果和空间 epoch | 不保存唯一业务事实，不构成强一致协议 |
| 导出 | Markdown、WikiLink、Obsidian ZIP | 知识可迁移、可离线阅读 | 不是数据库备份，也不等于与 Obsidian 双向同步 |

### 为什么选 Java？有必要吗？

不是因为“AI 必须用 Java”，而是这个项目的复杂度主要在企业业务治理：认证、组织、RBAC、并发审核、事务和任务状态。Java 适合承担这些长期维护的业务；Python 保留其内容处理生态优势。

**代价也要讲：**需要部署两种运行时，维护 HTTP 契约、共享文件路径、错误映射和超时。若只是个人资料整理，用 Agent + Markdown 或单 Python 服务可能更简单。

### 为什么先用模块化单体？

页面、修订、证据、审核在一次发布中要共同改变。放在同一业务服务和数据库事务内，容易定义和检查一致性。现阶段没有流量或团队规模证据证明必须拆微服务。

优先独立的是依赖重、资源需求不同的内容提取；未来按吞吐瓶颈考虑拆检索或处理 Worker，而不是先拆散强事务领域。

## 3. 数据模型：记住“当前态、历史、候选态”

| 概念 | 关键表 | 面试解释 |
| --- | --- | --- |
| 身份和协作 | users、organizations、workspaces、角色/权限/成员/会话相关表 | 定义谁在什么空间能做什么 |
| 原始资料 | sources、source_versions | sources 是可变元数据/当前状态，source_versions 保存版本内容与哈希；不能把两者都说成不可变 |
| 已发布知识 | wiki_pages、wiki_page_revisions | pages 便于快速读当前内容，revisions 保留历史与审核基线 |
| 引用和链接 | evidence、wiki_relations | evidence 关联页面修订与来源；relations 为 WikiLink 派生索引 |
| 候选变更 | change_sets、change_set_actions、reviews | 一份提案可改多页，批准前不混入正式知识 |
| 后台过程 | ingestion_jobs、query_messages、wiki_evolution_runs、ai_scheduled_task_runs | 保存排队、运行、错误、重试及结果 |
| 过程记录 | query_runs、audit_logs、outbox_events | 查询运行、操作审计和待发布领域事件 |

三个“版本”别混淆：

- **内容哈希**：标识内容、判断重复；不能代表审批先后。
- **页面修订 ID / 修订号**：记录一次已发布内容，是提案的基线和历史引用信息。
- **业务 version / 缓存 epoch**：分别用于并发检查和缓存命名空间，不是内容历史。

## 4. 核心流程一：资料到 Wiki

### 4.1 正常链路

1. 用户添加文本、网页或文件；文件先保存到本地对象目录。
2. Java 登记来源，写入适用的来源版本、摄取任务及审计/事件。
3. `IngestionCoordinator` 定期调用 `IngestionJobService.claim()` 领取任务。
4. 领取事务使用 `FOR UPDATE SKIP LOCKED`，把任务改为 PROCESSING，记录 owner、租约期限、尝试次数，随即提交。
5. 虚拟线程在领取事务之外做提取：文本复用已存内容，网页/文件/转写调用 Python。
6. `KnowledgeCompiler` 调用配置模型，解析结构化候选页面；不可用时可按 Markdown 章节确定性降级。
7. 回到完成事务：保存来源版本/状态，按 slug 匹配已有页面，生成多页面变更集。
8. 全是新增且提交者拥有直接发布权限，可发布；含已有页面更新或权限不足，进入审核。
9. 发布路径保存页面修订与证据，重建关系索引，更新任务和审计等状态。

### 4.2 为什么外部调用在事务外？

OCR 和模型请求可能耗时很长。若持有事务等待，会占用连接与锁，并把外部故障放大成数据库拥塞。

使用“短事务领取 → 事务外处理 → 短事务提交”，代价是要额外处理租约、重复执行和提交资格。**短事务是方向，不等于所有完成事务都很轻；大批量多页发布仍会增加锁时间。**

### 4.3 降级的意义与限制

章节拆分让材料不会因为没有可用模型就完全无法入库，但标题拆出的页面不一定是真正语义实体。多文档综合、消歧和矛盾识别能力不能用该降级机制冒充。

文件先存再登记数据库还存在“文件已落盘、数据库失败”的孤儿文件窗口。生产化应增加暂存状态、失败补偿或定期清理，不能宣称文件系统和 PostgreSQL 一次原子提交。

## 5. 核心流程二：审核和并发发布

### 5.1 批准流程

`ReviewService.approve()` 在一个事务中：

1. 锁定待审变更集，检查其仍可处理。
2. 对 UPDATE/ARCHIVE 目标按页面 UUID 排序后加锁，降低不同提案锁顺序交叉的概率。
3. 比较提案 `base_revision_id` 与页面 `current_revision_id`。
4. 基线不一致时，整份提案转为 SUPERSEDED，并记录原因，不覆盖新内容。
5. 基线有效时应用动作，写新修订及页面当前投影、证据和关系。
6. 写审核记录、审计和 Outbox，更新变更集状态；异常时相关数据库写入回滚。

### 5.2 面试举例

“A、B 两份提案都基于修订 R1。A 先通过，页面变为 R2。B 再审批时发现基线还是 R1，就失效，需要重新基于 R2 提交，而不是用旧内容覆盖 A。”

行锁控制发布时互斥，修订基线判断内容是否过期，更新条件中的 version 检查提供额外并发检测。三者作用不同。

### 5.3 审核的安全边界

当前要求已有知识经过审核业务流程，但这不等于落实“四眼原则”。具有审核权限的身份可以调用审核接口，MCP 也暴露审核工具。

**不能说“技术上只有人类能批准”或“提交人一定不能自审”。**若企业要求职责分离，应禁止自审、给自动化账户只授提交权限，对高敏知识增加二级审批。

## 6. 核心流程三：问 Wiki 与历史会话

### 6.1 会话为什么关闭浏览器还继续？

会话请求保存用户消息及 PENDING 助手消息，后台 `QueryConversationCoordinator` 领取助手消息完成查询。浏览器只负责展示/轮询，计算生命周期不绑定某条前端连接。

同一会话的活动助手消息受到检查和数据库部分唯一索引约束，避免上一条还没处理又同时产生第二个回答。不同会话可以并发。

这叫**持久化异步问答**，不是 token 流式 SSE，也不是“任何故障下都绝不中断”。Worker、数据库和模型仍可能失败。

### 6.2 检索与回答

1. 问题 Unicode NFKC 规范化，合并空白；最近会话可辅助追问理解。
2. 查缓存：组织 + 空间 + epoch + 页面/语义索引数据库指纹 + 检索文本/上下文/开关的哈希。
3. 未命中时检索已发布页面：全文、标题 trigram、正文 ILIKE 为关键词路；本地中文 BGE 512 维向量在 PostgreSQL real[] 做精确余弦检索，为语义路。
4. 两路各取最多 8 页，以 RRF 融合去重取 8 页，再补充最多 4 个一跳关系邻居。长文档保留语义命中片段进入回答上下文。
5. 给候选页建立编号、页面 ID、修订号、摘要等引用元数据。
6. 开启模型时按提示词要求基于这些页面回答；关闭模型时组合页面摘录。
7. 保存 answerMode、retrievalMode、语义降级原因、模型名、耗时、缓存命中情况、回答与引用。

当前模式包括 AI、EXTRACTIVE、MODEL_QUOTA、NO_KNOWLEDGE。普通模型异常也可能回落到摘录，不能说“开启大模型就必然调用成功”。

### 6.3 需要主动承认的检索边界

- 当前已有本地中文 Embedding 与 PostgreSQL real[] 精确检索；没有 pgvector/HNSW，也没有训练实体链接模型。实现、测试与限制见 [语义检索说明](SEMANTIC_RETRIEVAL.md)。
- 一跳 WikiLink 扩展可称“关系增强检索”，不应包装为完整 GraphRAG 社区聚合/多跳推理框架。
- `simple` 全文处理对中文有限，整句 ILIKE 不等同于中文语义理解。
- 已取消“无命中则返回最近 5 页”。语义召回有最低相似度阈值，但阈值不能替代业务评测，仍可能有误召回。
- 引用候选集是真实页面，不等于每条模型结论都被候选证据支持；目前主要依赖提示词，没有逐结论蕴含校验。
- 引用保存修订号，但当前前端通过页面详情读当前内容，不应宣称点击历史引用必然打开当时修订。

改进优先级：扩展问题/参考证据评测集，量化中文分词、语义召回和重排的收益，并根据规模评估 pgvector 近似索引。

## 7. 核心流程四：持续优化与定时资料任务

两者不是同一个功能。

| 功能 | 输入 | 目的 | 输出 |
| --- | --- | --- | --- |
| 持续优化 | 已发布 Wiki 页面快照 | 检查矛盾、过时表述和整理机会 | MAINTENANCE 审核提案及运行记录 |
| 网页持续刷新 | 已有网页来源 | 重新提取变化内容 | 摄取任务，复用编译和审核 |
| AI 定时资料任务 | 配置的任务指令/频率；厂商资讯任务还采集官方页面 | 收集新的资料 | TEXT 来源、来源版本、摄取任务与运行记录 |

### 7.1 AI 定时资料任务的具体链路

扫描到期定义 → 创建 run → 租约领取 → 官方页面采集（厂商资讯任务）→ 模型整理 → 创建来源与摄取任务 → 保存 run 结果 → 后续编译与审核。

厂商资讯采集与普通“问模型”不同：前者有外部网页证据；后者不能仅靠模型知识保证最新。来源网址和采集成功也不能自动保证日期过滤、完整性与事实正确性。

当前 `process()` 通过 `TransactionTemplate` 显式执行内部短事务，避免同类内部调用导致 `@Transactional` 代理不生效。**来源/摄取写入和 run 成功回写是分开的事务**，仍有来源已创建、run 未成功回写的崩溃窗口。

当前 run 可先标为 SUCCEEDED，表示结果已生成并进入后续摄取；摄取完成/失败再补充结果。因此面试要区分“模型成功”“编译成功”“已审核发布”，不要把三者当同一个状态。

### 7.2 开关和可观测性

任务支持启停、时间/频率配置、手动触发与运行记录；持续优化有独立开关和间隔。失败原因应明确呈现，保留历史，不为展示清除失败。

2026-09-08 的实际展示操作观察到模型 TLS 握手失败；它说明本地服务启动正常并不能证明外部模型链路始终可用。该现象未在本次文档整理中重新复现。

## 8. 认证、RBAC 与租户隔离

### 请求入口

- 自定义认证/授权拦截器，而不是使用 Spring Security。
- 密码通过 BCrypt 验证；访问凭证使用 JWT；刷新令牌通过 HttpOnly Cookie 传输并轮换，数据库保存摘要。
- 后端会复核会话、用户和成员等状态，而非只验 JWT 签名。
- MCP 接受 JWT 或 `lwk_` API Key，并检查 MCP_USE 和具体工具的业务权限。
- React 中的菜单/按钮权限不是最后安全边界。

### 数据库边界

业务数据包含 organization_id 和 workspace_id。进入租户业务事务后，`TenantDatabaseContext` 执行 `SET LOCAL ROLE llm_wiki_app` 和事务局部 `set_config`，配合 RLS。

`SET LOCAL` 随事务结束失效，避免连接池复用时残留上一位用户的上下文。后台任务不能假设 HTTP ThreadLocal 会自动传给虚拟线程，需要显式携带组织和空间。

**重要限制：**超级用户/BYPASSRLS 连接能绕过 RLS；FORCE RLS 不是对超级用户的万能约束。开发环境事务内降权，不等于生产可放心使用超级用户连接。跨租户调度又有 scheduler_mode 特殊策略，需要隔离权限并审计，不能把可设置的会话变量描述成不可突破的安全边界。

不用 Spring Security 的好处是控制路径直观；代价是需要自行承担登录限速、会话撤销、CSRF/CORS、Cookie、方法级鉴权覆盖等安全责任。不能说安全性因此更高。

## 9. MCP、模型配置和导出怎么讲

### MCP

`McpController` 实现初始化、ping、tools/list、tools/call 等 JSON-RPC POST 子集，复用既有业务服务。当前有查询、列页面、页面提案、文本来源和审核五类工具。

准确说法是“实现了 MCP 工具接入子集”，不是“全部协议能力和所有客户端兼容性都验证过”。当前没有依据宣称具备完整 OAuth 授权服务、SSE 恢复或所有传输能力。

### 模型配置

模型按空间配置，统一兼容客户端，配置连接测试与错误分类分离于密钥解密。测试通过只证明当次可用，不保证后续不超额度、不超时。密钥加密存储也依赖主密钥的安全保存和轮换。

### 导出

读取页面及相关数据后，在事务外生成 Markdown/Obsidian ZIP，减少打包阶段占用数据库连接。

当前 `ExportSnapshotService.load()` 标记 readOnly，但未显式设置 REPEATABLE_READ。不能仅凭“只读事务”宣称多条查询取得同一时刻快照；若需要严格一致导出，要明确隔离级别或统一版本边界。数据量大时还需考虑一次性加载全部页面的内存成本。

## 10. 项目最值得讲的工程亮点

这些是**场景化工程组合与产品设计**，不是新模型算法，也不是业内首次提出。

| 亮点 | 解决的问题 | 可展示的代码/产品证据 | 需要承认的代价 |
| --- | --- | --- | --- |
| 知识编译中间层 | 每次检索之外缺少长期整理成果 | 来源生成多页面，页面关联及历史 | 编译、维护额外消耗模型成本 |
| 提案与发布分离 | AI 直接覆盖正式知识的风险 | change_set、多页审核、基线失效 | 人工审核增加发布延迟和积压 |
| 自动化复用主链路 | 定时任务变成另一套直接写库旁路 | 任务结果先成为来源，再摄取审核 | 生命周期变长，需要阶段状态 |
| 持久化会话任务 | 关闭页面导致问答过程丢失 | 助手消息任务化、后台领取 | 不等于流式输出；要处理租约与重复 |
| 证据与版本一体化 | 无法解释知识是谁何时依据什么修改 | 修订、来源、审核与审计 | 有引用不等于事实验证完成 |
| 企业边界且保留开放出口 | 多人协作与知识迁移的冲突 | RBAC/RLS、MCP、Obsidian 导出 | 安全治理和协议维护成本 |

推荐强调前三项，再根据岗位追问展开事务、并发和安全。不要把“用了 Redis、JWT、虚拟线程”单独称作创新。

## 11. 容易被追问的一致性与可靠性

### 11.1 有 SKIP LOCKED 就不会重复执行吗？

不会。它避免领取事务对同一行同时加锁，但事务提交后，工作依靠租约。旧 Worker 卡住、租约过期、新 Worker 接管时，两边可能同时处理。

当前摄取完成路径先写来源/提案，最后更新任务时带 owner，但未见先锁定并校验当前领取代次、期限，也未检查这次任务更新影响行数。**不能保证过期 Worker 的业务写入被全部阻止。**

建议补充：每次领取生成 lease_token/fencing version，完成事务开头锁任务并校验 token、状态与期限，失效即回滚；外部耗时任务续租；对 job 对应结果建立幂等约束。多实例 owner 必须唯一，owner 本身也不能代替每次领取的代次。

### 11.2 每轮领取四个，就是最大并发四个吗？

不是。当前多个协调器共享 `newVirtualThreadPerTaskExecutor()`；上一轮未结束，下一轮仍能领取。轮询批大小限制提交速率的一部分，不是全局在途上限。

建议按模型供应商、租户、任务类型设置独立 semaphore/配额与背压，把 OCR/转写等重资源任务和轻量请求隔离。虚拟线程便宜，不意味着数据库连接、GPU 或模型额度无限。

### 11.3 Redis epoch 保证强一致吗？

不能。当前 epoch 在 Redis，发布方法在数据库事务结束前就递增；Redis 与 PostgreSQL 没有原子提交：

- 先递增 epoch、数据库尚未提交，读者可能把旧内容写进新 epoch 缓存。
- Redis 递增失败而数据库提交，旧缓存可能继续命中至 TTL 到期。
- epoch 读取失败回落 0，后续 Redis 部分恢复也不能简单等同于始终回源。

当前是尽力失效加 TTL。改进可把内容版本放到 PostgreSQL，随发布事务递增，以持久版本作为读写缓存的依据；提交后事件负责清理/预热。若只采用 afterCommit 或 Outbox，要明确它缩小窗口、提供补偿，不自动成为严格强一致。

### 11.4 有 Outbox 就有消息恰好一次吗？

没有。当前 OutboxPublisher 读取事件、输出 info 日志、标记 PUBLISHED，未接外部 Broker。日志已输出但事务回滚，重试会重复输出。

可以说“业务事实与事件记录同事务”，不能说“外部消息和数据库原子提交”。未来接 MQ 应按至少一次投递设计，消费端按 eventId 去重并设置重试/死信。

### 11.5 所有关系都能实时重建吗？

审核发布和摄取发布调用 WikiRelationIndexer。但手工直接创建的 PageService.publishNew 当前未调用该索引器，也未见 Outbox 有关系消费逻辑。

此外索引器按 slug 匹配当时已经存在的页面；目标稍后才创建，不会天然补齐之前漏掉的反向关系。需要统一发布服务、补建目标后的入链或周期性重建。

### 11.6 安全抓取就完全没有 SSRF 了吗？

Python 校验协议、DNS 解析地址和每次重定向，限制下载大小与文件根路径，这是已有防护。DNS 检查与实际 HTTP 连接之间仍需考虑地址变化/重绑定，生产还应依赖出站网络隔离、连接目标约束和服务间认证。不要用“绝对防 SSRF”措辞。

## 12. 高频问答：可以直接练习

**Q：为什么不直接把 Markdown 放本地？**

A：本地 Markdown 适合个人使用。企业协作需要事务、权限、修订、审核和并发写，数据库更适合承载这些事实；同时用通用导出保留可迁移性。代价是部署和运维更重。

**Q：为什么暂时没上向量数据库？**

A：已经接入向量召回，但没有引入独立向量数据库。本机 PostgreSQL 没有 pgvector，当前用 real[] 保存本地 BGE 向量并做精确余弦检索。优点是复用租户、事务、备份和运维；代价是扫描复杂度随块数增长。后续用真实负载决定迁移 pgvector/HNSW 的时间，而不是把精确扫描称为 ANN。

**Q：为什么图谱不直接用 Neo4j？**

A：当前查询主要是一跳邻居和可视化，用关系表足够表达，也便于与发布事务共同更新。深层路径分析与大规模图计算有明确需求后，再评估图数据库收益。

**Q：AI 胡说怎么办？**

A：把风险分成入库与问答。入库侧已有知识先提案审核；问答侧检索已发布知识并返回引用。但目前没有逐结论验证，不能承诺零幻觉。需要拒答、证据校验、人工反馈和评测继续约束。

**Q：你做的优化提升了多少？**

A：当前没有足以公开承诺的压测与问答评测数据。我能说明减少重复综合、缓存及一跳批量扩展的机制，但不会给虚构百分比。后续按真实问题集、数据量与并发模型测量。

**Q：最难的点是什么？**

A：不是调通模型接口，而是让不稳定的外部模型结果进入可控业务流程：任务可恢复、已有知识不被旧提案覆盖、来源和修订能追溯，同时不把外部调用包进长事务。

**Q：单体能扩展吗？**

A：数据库领取提供多实例协作基础，但扩展前必须补齐租约 fencing、唯一实例身份、全局在途限流和数据库权限治理。不能从“用了 SKIP LOCKED”直接推导已经具有完整集群可靠性。

**Q：浏览器关闭，为什么后台不取消？**

A：用户消息与助手占位记录先持久化，服务端任务继续消费。前端回来读取同一会话状态。这是任务化，不是依靠前端持续持有网络请求。

**Q：现在能不能直接作为成熟企业 SaaS？**

A：完成了企业功能骨架与可运行链路，但仍是持续开发阶段。多租户安全审计、限流、租约幂等、缓存一致性、备份恢复、性能指标与运维都需要进一步验证和完善。

## 13. 可以讲的故障案例

### 案例 A：上传 DOCX 后 Python 返回 422

- 现象：Java 侧来源已登记，提取失败提示 `Field required [body]`。
- 应讲的定位思路：分开检查文件内容、Java 请求体、Content-Type 与 FastAPI 模型契约；422 缺 body 首先是请求契约问题，不能直接归咎于文件损坏。
- 当前可指向的代码：PythonExtractionClient 的 JSON 请求构造、Python 的 FileExtractRequest。
- 不要说：本次文档整理重新复现并验证了所有格式。

### 案例 B：有内容，没有可用实体或关系

- 编译质量问题与关系索引问题必须区分：前者看结构化多页输出/降级策略，后者看发布路径是否调用索引以及链接目标是否存在。
- 本项目已有多页编译和章节降级，但手工直接创建缺少关系索引调用仍是边界。
- 面试价值：从“页面存在”追到“内容、候选页、发布、派生索引”分阶段定位。

### 案例 C：模型错误被错误归因为密钥解密

- 额度限制、网络/TLS、服务商错误与本地解密不是同一类问题。
- 当前有配额异常分类、连接测试和回答模式记录，但其他模型异常仍可能降级且提示不够具体。
- 改进方向：统一结构化错误码、阶段字段、重试建议，日志不泄漏密钥。
